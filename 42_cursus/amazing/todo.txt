[ ] 4. The 3x3 rule is not implemented

    Bullet 5 of the eval sheet: no 3x3 or larger open zone without walls.
    Nothing in the code forbids one. Grep the repo — the rule appears
    nowhere outside your peer's test branch.

    It is a real, reproducible failure, not a theoretical one:

        20x15, seed 3, PERFECT=False, kruskal
        -> open 3x3 block with its corner at (11, 12)

    Why it happens: a perfect maze CANNOT hold a 3x3 room — a spanning
    tree has no room for the twelve passages one needs. But _braid()
    (generator.py:189) and _loosen() (generator.py:210) both open walls
    after the carve, and neither looks at what it is opening into.
    So this is a PERFECT=False bug only.

    Where it belongs: MazeGenerator, not the subclasses. You said this
    and the code agrees — all three algorithms inherit _braid/_loosen,
    so one guard there covers kruskal, backtracker and division at once.
    Shape it like _touches_42() (generator.py:169): a question asked
    before a wall comes down, not a repair pass afterwards.

        def _would_open_a_room(self, cell, side) -> bool:
            ...  # would this wall leave a 3x3 with nothing standing?

    then refuse such walls in _braid and _loosen the same way
    _touches_42 already refuses the 42's walls.

    Your peer already wrote the test. Do not write a second one:

        git checkout origin/test/evaluation -- tests/test_eval_maze.py

    It brings walled_inside() and open_rooms() helpers and two tests —
    a sweep over both algorithms x both modes x 3 sizes x 4 seeds, plus
    the 20x15/seed-3 case pinned on its own. Both fail today.


[ ] 5. _loosen is quadratic — PERFECT=False only

    src/mazegen/generator.py:210 (_loosen), :245 (_choke_points)

    Measured, kruskal, PERFECT=False:

        18x9    0.5s
        20x15   1.1s
        30x20   5.3s
        40x30  18.6s
        50x50  91.9s

    PERFECT=True is unaffected and instant. Profile of the 20x15 run:
    3.71 of 3.75 seconds inside _choke_points.

    The cause is plain: _choke_points runs one full BFS (region_of) per
    open passage — 348 BFS sweeps on a 20x15 — and _loosen's `while True`
    recomputes the whole set after every single wall it opens.

    The docstring already names the cure, so this is finishing a sentence
    the code started:

        "The linear way is to look for bridges in one pass; this stays
         as the version that is plainly right."

    Tarjan's bridge-finding is one DFS, O(V+E), and returns every bridge
    at once. A choke point here is a bridge that separates entry from
    exit specifically, so: find the bridges, build the 2-edge-connected
    components, and the chokes are the bridges on the path between
    entry's component and exit's.

    Keep the old _choke_points under a test as the oracle — it is
    "plainly right" and slow, which is exactly what you want to check a
    fast version against. Same maze, same seed, same answer.

    NOTE: this interacts with item 4. If the 3x3 guard refuses some
    walls, _loosen can run out of legal walls to open, and it must end
    rather than spin. It already has that shape (`if not across: return`)
    — keep it when rewriting.

[ ] 6. Centralise the exception types

    Three conventions in play today:

      - app/config.py is the good one. Everything funnels into
        MazeConfigError, messages name the key and the value.
      - the library raises bare builtins: ValueError and IndexError
        across maze.py, generator.py, config.py, solver.py.
      - rainbow has UnknownColour; the GUI has TooSmall; the terminal
        has TooSmallTerminal.

    The cost is at a_maze_ing.py:264:

        except (MazeConfigError, ValueError, OSError,
                TooSmallTerminal, gui.TooSmall) as error:

    Catching bare ValueError means a genuine bug anywhere below is
    caught and printed as "error: ..." like a user mistake, exit 1.
    A defence question you do not want.

    Suggested: a MazeError base in mazegen, with ConfigError,
    GenerationError and SolverError under it. Then that clause names
    MazeError and the renderers' own, and a stray ValueError crashes
    loudly the way a bug should.

    Do this AFTER 4 and 5 — both touch generator.py, and rebasing an
    exception refactor across them is wasted work.
